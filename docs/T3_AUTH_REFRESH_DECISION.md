# AUTH DESIGN DECISION REQUIRED

1. **Missing capability:** rotating refresh credentials with replay detection and per-session revocation. No refresh endpoint or refresh token is implemented in this pass.
2. **Current-schema limit:** users.auth_version can invalidate every credential for an account, but cannot identify a session, record a used refresh token, or distinguish concurrent sessions. Reusing this one integer as a rotation counter would force all devices to share one credential generation and would not provide session-level replay handling.
3. **Smallest viable options:** (A) approve persisted rotating sessions; (B) approve stateless, purpose-bound refresh JWTs checked against current account state/auth_version, accepting replay until expiry and account-wide revocation only. Neither option is silently selected.
4. **Recommendation:** A. Keep the access-token and account-wide logout changes; approve the session design separately before adding refresh issuance.
5. **Schema impact:** A adds one auth_sessions table referencing dogfood.users, with session ID, current refresh-token digest/generation, expiry and revocation state, plus the indexes/constraints needed for atomic rotation. Bind refresh credentials to the session and generation so a valid old credential can revoke its session on replay. Exact columns, lifetime, concurrent-refresh policy and migration require owner review. B adds no database objects. This pass adds no table, column, constraint or migration.
6. **Security tradeoff:** A enables atomic rotation and per-session revocation, with persistence and concurrency-policy complexity. B leaves a stolen refresh token replayable until expiry/global invalidation; logout affects every device. Account-wide logout implemented here increments users.auth_version atomically and does not claim per-session revocation or recall requests already authenticated before invalidation.
